# Predefined topics — prototype implementation

Public opinions now receive zero or more categories from [topic_catalogue.json](../../opinions/topic_catalogue.json). The live website can browse these stored memberships using the example directory’s visual style. Specific discussion subjects, stance and supporting arguments remain separate future work.

## Input to topic membership

1. Save the original Contribution with its stable source ID and declared visibility.
2. For public input, compute the existing BGE-M3 document embedding and sentiment score.
3. Compare that vector with BGE-M3 embeddings of each catalogue description and its two reference texts. Cache the small reference matrix once per process.
4. For each topic, retain its strongest cosine similarity. Accept the strongest topic only when its score reaches `minimumSimilarity` (initially 0.52). Accept additional topics only when they also reach `minimumSecondarySimilarity` (0.58) and lie within `maximumScoreGap` (0.08) of the strongest match. These values live in the catalogue, not in the UI.
5. Store all accepted IDs and the decision record with the linked Opinion. No qualifying topic produces an empty array, shown under **Other / unassigned**.

The stronger requirement for secondary topics reduces incidental matches while allowing an input about housing and transport to appear under both. A topic match estimates subject matter; it does not establish agreement, a supporting reason or a contributor’s own chosen category. Similarity is not calibrated confidence.

Inference runs before the database write transaction in the submission pipeline. A classification failure retains the source and returns `503 topics_unavailable`; retrying the same submission key resumes the work without duplicating opinions. New opinions created through the model/admin also receive labels. Bulk imports bypass model hooks and need the backfill command.

## Stored evidence and boundaries

`Opinion.topic_ids` is a PostgreSQL array with a GIN index, so a category can be filtered directly without a vector comparison. An opinion can occur in several categories, but appears once within any category. The legacy `Opinion.topic` string and `Cluster` relation remain independent; the EVōC experiment on its own branch can later provide discovered subjects beneath these categories.

`Opinion.topic_analysis` records:

- Method identifier and embedding-model name; the model revision used for the reference vectors when available.
- Catalogue version and content hash, plus all three decision thresholds.
- Hash of the original text and of the opinion vector used for comparison.
- Classification time and every topic’s similarity, winning reference index and assignment decision. Reference index 0 is the description; indices 1 and 2 identify the catalogue examples.

The source link, stored opinion vector, decision metadata and Git-versioned catalogue make the current assignment inspectable. No explanatory quote or rationale is generated by an LLM. This prototype stores the latest analysis only: `--all` replaces it. Historical analysis runs, opinion-embedding model revision tracking and automatic reanalysis after text edits require a later extension.

## Browsing API

- `GET /api/v1/topics/` returns `catalogueVersion`, `totalOpinions` and `topics`. Each topic has `id`, `title`, `description`, `opinionCount` and `lastContributionAt` (ISO timestamp or null). The response also includes the `unassigned` group. All counts use stored Opinion records; example fixtures and private Contributions are excluded.
- `GET /api/v1/opinions/?topic=housing` returns the newest 50 members, ordered by timestamp and ID. It runs no model. Distance and similarity are null for this browse request.
- Add `query=...` to search within the assigned topic. Retrieval and membership filtering happen before the 50-result cap.
- Opinion results additionally include `topics` (ID/title pairs), `createdAt` and `topicAnalysis`. The existing [search contract](SEARCH_API.md) otherwise remains unchanged.

The UI sorts topics by number of opinions, latest contribution or title. A topic opens a sentiment overview and original text, with links to any other assigned topics. The chart still covers only the returned opinions; the directory count covers all stored members. Counts across categories overlap and are neither unique participants nor national population estimates.

## Operation and iteration

Apply the generated `0006_opinion_topics` migration, then classify existing embedded opinions:

```sh
docker compose run --rm web uv run python manage.py backfill_topics
```

Normal reruns skip opinions with an analysis record. To change topics or thresholds, edit the catalogue, increment its version, rebuild/restart the backend, then run:

```sh
docker compose run --rm web uv run python manage.py backfill_topics --all
```

The command streams opinions in batches and updates only topic fields. It never publishes private inputs or overwrites original text, existing sentiment, source IDs or embeddings. Topic browsing uses database reads; classifier work is proportional to the fixed catalogue size rather than the total number of opinions. For larger deployments, move this repeatable work into a durable worker and maintain topic counts incrementally instead of aggregating the full table on each directory request.

The initial thresholds and reference wording were adjusted using a small set of hand-written civic, mixed-topic, German, French and unrelated inputs. This is a development check, not an independent accuracy benchmark. Whole-input embeddings can miss secondary subjects or assign adjacent categories incorrectly. Evaluation on new inputs, contributor corrections and statement-level analysis should precede stronger claims about classification quality.
